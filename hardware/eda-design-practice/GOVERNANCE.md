# 什么能进这个 skill

## 为什么需要门槛

代价是**不对称**的：

| | 后果 |
|---|---|
| **漏掉一条规则** | 下次重新推一遍。费时间，但结论是对的 |
| **错误提升一条规则** | 在不适用的场合**被自信地照做**，而且不会有人去质疑它 |

所以**默认拒绝**。宁可留在项目 CLAUDE.md 里。

## 晋升路径

```
项目 CLAUDE.md        ← 所有新知识的默认落点，零门槛，发现时随手记
      ↓ 二次命中
candidates/           ← 候选区，带出处，等第二次验证
      ↓ 人工逐条确认
references/           ← 通用规则
```

### 判据一：二次命中

一条规则必须在**两个不同项目里独立撞到**才够格。
一次是巧合，两次才是模式。这个判据客观、可核对，不靠感觉。

**例外**：首次命中但**机理清楚且代价严重**的，可以直接晋升，但必须写满五个字段。
例：「直连线路径碰撞检查」只在 daikin-rcu 出现过一次，但机理是 EasyEDA 的 T 形连接语义
（确定的、与项目无关），代价是静默短路（图上看不出来）→ 直接晋升。

### 判据二：这条依赖什么

问：**换一块板、换一颗芯片、换一个客户，它还成立吗？**

| 依赖于 | 归属 |
|---|---|
| **人怎么看图** | 通用 ✓ |
| **EDA 软件行为** | 通用 ✓，**必须标客户端版本** |
| 具体芯片 / 封装 / 数值 | 项目内 ✗ |
| 客户偏好 | **用户偏好层**，不是技术规则 ✗ |

第四类要单独分出来。它是真的、要遵守（例：「图一律用 Mermaid，不画 ASCII art」），
但它不是工程知识，混进技术规则里会让规则库失去权威性。

## 每条通用规则必须带五个字段

```markdown
### <规则名>
**场景**：什么时候适用
**机理**：为什么 —— 不能只写「要这么做」
**代价**：不遵守会怎样（最好带真实事故 + 项目名 + 日期）
**出处**：哪个项目、哪一次
**失效条件**：什么时候这条**不**适用
```

★ **「失效条件」是核心过滤器。**
如果说不出边界，通常说明还没真正理解这条规则 —— 那就不该晋升。

## 一律打回的四类

1. **表述为「不能 X」却说不出为什么的禁令**

   反面教材：canmv_serdes 曾记「netflag 用 `create` 会挂死，**只能**用带网络名的短导线代替」。
   本项目（daikin-rcu）证伪：有专用的 `createNetFlag`，工作正常。
   真相是「`create` 对 netflag 挂死（3.2.186），**正确入口是 `createNetFlag`**」。
   当初若被要求写机理和失效条件，就会问「是所有入口都不行，还是我只试了一个？」——
   大概率当场发现。

2. **绑死具体数值**：`Vstore 取 10V`、`CACT 100nF`、某个 uuid、某个料号

3. **绑死一次性环境**：「今晚 bridge 断了 7 次」
   —— 现象是临时的，但「批量写必须可重入 + 断线重试」是通用的（见下：上提）

4. **是需求不是规则**：「用户这次要 USB-C」

## 关键动作：从具体现象里提炼上位规则

晋升时最有价值的一步。具体数值留项目，**机理上提**。

| 项目内的现象 | 上提后的通用规则 |
|---|---|
| MB10S 的引脚 x 偏移 ±25，原点要放 x=…5 | **封装引脚偏移决定原点落整格还是半格；放完必须全量查栅格，不落栅格 = 网表里就是断的** |
| 今晚 bridge 断了 7 次 | **批量写必须可重入（先清后建）+ 断线自动重连重试** |
| 这颗 QFN 的 EP 是 2.6mm | **库封装只能从名字读尺寸（`lib_Footprint.get()` 不回焊盘几何）；引脚方位只能在 PCB 上读焊盘世界坐标验证** |

## 反向校验（退役机制）

skill 里的规则被观察证伪时，**必须当场改掉并标注**，不能默默绕过：

```markdown
~~netflag 只能用短导线代替~~  ← 2026-09-28 于 daikin-rcu 证伪，见上
```

规则库的价值全在可信度。留一条错的会污染全部。

## 操作节奏

- **发现时零摩擦**：撞到就往项目 CLAUDE.md 记，不判断归属
- **收尾时批量评审**：项目做完出一份晋升提案，一条一行，人逐行说收/不收

```
[晋升] GND 就近连接          二次命中(serdes/daikin)  可读性
[晋升] 直连线路径碰撞检查     首次但机理清楚+代价严重   EDA行为
[修正] netflag 禁令          本项目证伪 → 改写为带版本的事实
[留项目] CACT=100nF          依赖芯片
[打回] QFN 的 TL/BL 方位     只观察到一次，机理不明
```

**不确定的默认不收。**

## 能被代码检查的规则，优先写成代码

写在文档里的规则靠自觉，写进 `lib/` 里的检查器每次都会跑。
能程序化的一律程序化（栅格、重叠、网表、符号朝向），文档只留说不清的判断题。

## 一个有效的提炼手法：请人**手工改半页**做示范

daikin-rcu 2026-09-28：用户想说「符号别一个个散着放，该连的连起来」，
一开始是口头描述，我照着实现会走样。后来用户**直接在编辑器里手工改了半页 P2**，
然后说「这次的改动你可以废掉」——

**那半页图就是规格。** 从它反推出来的东西，比任何口头描述都准：

- 哪些该合并（间距 70~80 的电容组、分压电阻串）→ 定出了距离阈值 110
- 哪些不合并（跨半页的）→ 定出了失效条件
- 整条网连成一坨时**一个符号都不留**（VBUS_EN / BOOT_N）→ 推出了 R2 的推论
- 电源地即使连成一坨也留**一个**符号 → 推出了例外

★ **所以：人手工改的东西，在废弃之前一定要先存成参照。**
`--snapshot` 到一个单独的参照目录（不要覆盖正式快照），代价一条命令。

★ **验证规则是否泛化对了，判据是「能不能复现人的判断」**：
P2 的 11 条网络里 7 条符号数和人手工结果完全一致，另 4 条是人还没轮到的。
这比「我觉得好看」硬得多。
